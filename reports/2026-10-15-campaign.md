ranking. The owner authorized the entire [candidate matrix](2026-10-15-campaign-plan.md).

Downloads overlap inference, so these are desktop-use timings, not quiet benchmarks.

## History and a harder language task

`context-v1` completed in **134.172 seconds**, seven API turns over two user
messages. It recovered all three ledger markers, re-read runtime revision 2,
retained the zero retry setting, and returned null for the missing port. The
second turn read the current runtime file. The earlier ledger was unavailable
to the tool on that turn, but Qwen reused delivered history without trying the
failing read. Thus transient-error recovery itself was not exercised by this run.
This is not a 64K-context reliability result.

The held-out `ts-sql-v1` task finished in **289.812 seconds**, five API turns,
with correct source discovery and absent-database-URL honesty, but failed code
requirements:

- TypeScript compiles under strict TypeScript 5.9.3; **5/6 behavior groups pass**.
  It checks object/non-null but accepts non-plain objects that have a valid id.
- SQLite migration fails with **FOREIGN KEY constraint failed** on populated
  source tables. It tries to disable foreign keys after starting a transaction.
- Both rename statements also omit `RENAME`: `ALTER TABLE jobs_new TO jobs`
  is invalid SQLite syntax. That statement was not reached in the populated
  migration test; the syntax finding comes from source review.

The unchanged answers are retained locally. The unrestricted-thinking rerun
finished in **228.641 seconds** with fewer tool rounds. It corrected the rename
syntax but still failed the same non-plain-object group and the populated
migration: it drops the parent before the referencing child table with foreign
keys enabled. Thus both thinking settings yield 5/6 TypeScript groups and a
failed migration on this task. The extended ledger test completed in **243.828
seconds** and passed the six factual/current-file checks. Its ledger contains
21,461 Qwen tokens; the last request was about 26,336 tokens with history and
template overhead. This does not establish full 64K reliability.

## Restart recovery and current memory

15 October** (User32 1074, MoUsoCoreWorker and TrustedInstaller). The current
boot began at 01:34:45. The surrounding event window contains no new WHEA,
bugcheck or display-driver crash, and no new minidump was found. This incident
must not be attributed to the earlier hardware failures or RAM speed.

The Qwen batch512/ubatch128 trial was interrupted by the update. Its last sample
had 6.606 GiB free RAM, 4089 MiB free VRAM and GPU core 42 C. Partial generation
was about 21.93 tok/s, but there is no complete answer: **unscored interruption**.
The earlier completed answers and isolated grades survived. Windows Update
settings, drivers and clocks were not changed during recovery.

Unloaded free RAM now fluctuates around **15–19 GiB**, versus roughly 26 GiB
before the restart. Existing applications remain open. Profiles are being
reassessed against current memory rather than assuming yesterday's fit.

## Gemma dense placement probes

The official Gemma 4 31B QAT artifact completed full size/SHA256 verification.
At 16K context, all attention on GPU and all 60 dense FFNs on CPU, the runtime
reported **5655 MiB GPU model buffers, 12265 MiB host model buffers and 1211 MiB
q8 KV cache** (680 MiB global plus 531 MiB sliding-window). GPU KV left only
223 MiB free VRAM, so the existing 400 MiB guard stopped the server before the
coding task. This is a resource rejection, not a model quality score.

A `--no-kv-offload` retry keeps the same q8 KV in system RAM. One attempt was
rejected before loading when free RAM was 15.13 GiB; a later fresh snapshot
passed the 17.5 GiB gate. That attempt loaded and returned `READY` in 8.30 s.
The five-token smoke measured only 1.02 generation tok/s; the longer calibration
is in progress. Process dedicated VRAM at readiness was 5.98 GiB, and RAM during
the first calibration samples was 13.73 GiB. Shared WDDM memory overlaps RAM and
is not an additional allocation to add to these figures.

## Validation and interpretation

Generated code ran only inside Linux/bubblewrap namespaces, with a cleared
environment, separate network/process namespaces and no host home/drive mounts.
Node 24.22.0 and TypeScript 5.9.3 were pinned and verified against their publishers'
SHA256/SHA512 metadata. They are installed under the designated data drive.

The TypeScript/SQLite grader passes a hand-written positive control (6/6 each)
and detects the negative controls (1/6 TypeScript and 2/6 SQLite). Code behavior,
source grounding, test packaging and latency are reported separately. No model
has been promoted on the basis of these small tasks, and editor validation of
the eventual finalists remains part of the campaign.
