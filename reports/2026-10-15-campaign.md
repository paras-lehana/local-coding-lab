# Autonomous model campaign — live evidence

**In progress, 15 October 2026.** This is a checkpoint, not a completed model
ranking. The owner authorized the entire [candidate matrix](2026-10-15-campaign-plan.md).
Apps remain open. Each whole prompt, including tool turns, has a 20-minute limit.
Downloads overlap inference, so these are desktop-use timings, not quiet benchmarks.

## History and a harder language task

`context-v1` completed in **134.172 seconds**, seven API turns over two user
messages. It recovered all three ledger markers, re-read runtime revision 2,
retained the zero retry setting, and returned null for the missing port. The
second turn read the current runtime file. The earlier ledger was unavailable
to the tool on that turn, but Qwen reused delivered history without trying the
failing read. Thus transient-error recovery itself was not exercised by this run.
This is not a 64K-context reliability result.

The held-out `ts-sql-v1` task finished in **289.812 seconds**, five API turns,
with correct source discovery and absent-database-URL honesty, but failed code
requirements:

- TypeScript compiles under strict TypeScript 5.9.3; **5/6 behavior groups pass**.
  It checks object/non-null but accepts non-plain objects that have a valid id.
- SQLite migration fails with **FOREIGN KEY constraint failed** on populated
  source tables. It tries to disable foreign keys after starting a transaction.
- Both rename statements also omit `RENAME`: `ALTER TABLE jobs_new TO jobs`
  is invalid SQLite syntax. That statement was not reached in the populated
  migration test; the syntax finding comes from source review.

The unchanged answers are retained locally. The unrestricted-thinking rerun
finished in **228.641 seconds** with fewer tool rounds. It corrected the rename
syntax but still failed the same non-plain-object group and the populated
migration: it drops the parent before the referencing child table with foreign
keys enabled. Thus both thinking settings yield 5/6 TypeScript groups and a
failed migration on this task. The extended ledger test completed in **243.828
seconds** and passed the six factual/current-file checks. Its ledger contains
21,461 Qwen tokens; the last request was about 26,336 tokens with history and
template overhead. This does not establish full 64K reliability.

## Gemma dense placement probes

The official Gemma 4 31B QAT artifact completed full size/SHA256 verification.
At 16K context, all attention on GPU and all 60 dense FFNs on CPU, the runtime
reported **5655 MiB GPU model buffers, 12265 MiB host model buffers and 1211 MiB
q8 KV cache** (680 MiB global plus 531 MiB sliding-window). GPU KV left only
223 MiB free VRAM, so the existing 400 MiB guard stopped the server before the
coding task. This is a resource rejection, not a model quality score.

A `--no-kv-offload` retry keeps the same q8 KV in system RAM. One attempt was
rejected before loading when free RAM was 15.13 GiB; a later fresh snapshot
passed the 17.5 GiB gate. That attempt loaded and returned `READY` in 8.30 s.
The five-token smoke measured only 1.02 generation tok/s. The longer calibration
hit its **300.016-second deadline**, with the server reporting 259 generated
tokens at **0.95 tok/s**. It fails the research's 3.5 tok/s practical gate for
this profile; its partial coding answer receives no quality score. This is not
a measured rejection of every possible dense configuration.

Process dedicated VRAM at readiness was **5.98 GiB**; peak sampled process RAM
was **14.57 GiB**. Minimum free RAM/VRAM during this attempt were **4.97 GiB /
793 MiB**, and maximum GPU core temperature was 49 C. Shared WDDM memory overlaps
RAM and is not an additional allocation to add to these figures. The server
cancelled the task at the deadline and the owned launcher unloaded it.

The dense weights were subsequently re-hashed against the publisher SHA256,
recorded in the local retention log, and deleted as the owner authorized.
All answers, logs, profiles and metadata remain. The verified Qwen Q4 baseline
is retained; cleanup reclaimed 16.44 GiB.

## Gemma 26B QAT: repeated core and history results

Full artifact size and SHA256 passed before loading. The balanced 32K profile
places experts from the first 24 blocks on CPU and the final six on GPU, with
attention on GPU throughout. Measured model buffers are **3954 MiB GPU / 10379
MiB host**. q8 KV is **473 MiB** (340 global + 133 sliding-window), and the GPU
compute buffer is 414 MiB. At readiness the process used **4.97 GiB dedicated
VRAM**; sampled RAM rose from about 10.95 to 12.21 GiB during early tool rounds.

The smoke returned `READY` in 1.47 seconds. Four core answers have now been
reviewed and graded in isolation:

All four read six distinct source files; seed 75 read the code twice. The three
bounded runs average 375.407 seconds (sample standard deviation 58.393 seconds),
with aggregate generation rates of 15.21–16.41 tok/s. They correctly identify
version precedence, explicitly read linked sources and avoid inventing the absent
port/timeout or claiming test execution. Some seed-73 line citations point to
adjacent lines. The unrestricted run supplies correct replacement code but does
not demonstrate a quality advantage for its extra time on this small task.

For seed 73 and unrestricted thinking, the standalone test block omits an active
function import and fails with missing-function NameErrors. Combining the two
unchanged blocks, as their stated in-scope assumption permits, passes every test.
These are packaging assumptions, not syntax errors or separate algorithmic bugs.
Generated-test coverage still misses some empty values and mutable objects nested
inside lists; the independent groups cover those cases.

The 120-record history test completed in **247.109 seconds**, eight API turns
over two user messages. All six requested values are correct: three earlier
ledger markers, freshly read runtime revision 2, zero retries and null for the
missing port. Its actual phase-two read is `docs/runtime.md`, as reported. It did
not attempt the unavailable ledger read, so transient-error recovery remains
unexercised. This is short-history evidence, not a passed 64K-context claim.

The native embedded template parsed actual file-tool calls. Runtime generic
`--reasoning-preserve` reports unsupported, but a live `/apply-template` check
of an actual recorded continuation preserved **both prior tool-call thought
blocks** and emitted the native thought marker. The embedded template's explicit
`preserve_thinking` setting works for that tested continuation; this is not a
claim that editor clients transport the same history correctly.

A separate 640-record history case was frozen before collection. Its ledger has
43,228 tokens with this model's tokenizer, excluding template/chat overhead.
The original 120- and 320-record case hashes remain unchanged. A 64K follow-up
profile is proposed, not yet measured; larger context alone earns no recall score.

## Validation and interpretation

Generated code ran only inside Linux/bubblewrap namespaces, with a cleared
environment, separate network/process namespaces and no host home/drive mounts.
Node 24.22.0 and TypeScript 5.9.3 were pinned and verified against their publishers'
SHA256/SHA512 metadata. They are installed under the designated data drive.

The TypeScript/SQLite grader passes a hand-written positive control (6/6 each)
and detects the negative controls (1/6 TypeScript and 2/6 SQLite). Code behavior,
source grounding, test packaging and latency are reported separately. No model
has been promoted on the basis of these small tasks, and editor validation of
the eventual finalists remains part of the campaign.
