ranking. The owner authorized the entire [candidate matrix](2026-10-15-campaign-plan.md).

Downloads overlap inference, so these are desktop-use timings, not quiet benchmarks.

## Gemma dense placement probes

The official Gemma 4 31B QAT artifact completed full size/SHA256 verification.

reported **5655 MiB GPU model buffers, 12265 MiB host model buffers and 1211 MiB

A `--no-kv-offload` retry keeps the same q8 KV in system RAM. One attempt was
rejected before loading when free RAM was 15.13 GiB; a later fresh snapshot

hit its **300.016-second deadline**, with the server reporting 259 generated
tokens at **0.95 tok/s**. It fails the research's 3.5 tok/s practical gate for
this profile; its partial coding answer receives no quality score. This is not
a measured rejection of every possible dense configuration.

Process dedicated VRAM at readiness was **5.98 GiB**; peak sampled process RAM
was **14.57 GiB**. Minimum free RAM/VRAM during this attempt were **4.97 GiB /
793 MiB**, and maximum GPU core temperature was 49 C. Shared WDDM memory overlaps
RAM and is not an additional allocation to add to these figures. The server
cancelled the task at the deadline and the owned launcher unloaded it.

The dense weights were subsequently re-hashed against the publisher SHA256,
recorded in the local retention log, and deleted as the owner authorized.

The 120-record history test completed in **247.109 seconds**, eight API turns

The held-out TypeScript/SQLite answer completed in **347.078 seconds**, six API

did not run. Source review additionally finds no plain-object prototype check;

The unchanged migration fails on the populated database with **FOREIGN KEY
constraint failed**. It attempts to disable enforcement inside an active
transaction. It also wrongly changes `jobs.id` from INTEGER to TEXT, treating
the TypeScript string-id requirement as a database requirement. This mixes two
contracts that were separately described in the supplied file. Neither the
successful Python samples nor official QAT compression prevents these defects.
The answer invents no deployment URL and claims no test execution, though it
omits the requested explicit statement of tests actually run.

`preserve_thinking` setting works for that tested continuation; this is not a
claim that editor clients transport the same history correctly.

The server log records activation of the 2048-token reasoning budget and

ceiling is observed runtime behavior for this template, not just an accepted
HTTP field. It is still not a trained native effort level such as "xhigh".

A separate 640-record history case was frozen before collection. Its ledger has

## GLM collection and conditional precision trials

GLM Q4 passed full hash verification, loaded and returned `READY` in 0.563 s.
At 32K, the loader reports **3725 MiB GPU model / 12974 MiB host model**,
**899 MiB q8 KV** and **137 MiB GPU compute**. Readiness dedicated process VRAM
is **4.90 GiB**; early tool-round sampled RAM is about **13.40 GiB**. These are
load measurements; its coding answers still require review. An actual recorded
continuation renders its preceding thought block with `clear_thinking:false`.
That verifies this template continuation, not editor transport.

The first core answer (seed 73, 2048 ceiling) completed in **226.844 seconds**,
two API turns and seven successful reads. Source inventory and absent-fact
honesty pass review, but its implementation passes only **1/6 independent
Python groups** and **2/14 of its own tests**. Its added isolation assertions
wrongly require identical keys, types and immutable values before and after
valid overrides. These assertions reject legitimate merges. One generated test
also wrongly expects an empty-dictionary override to erase nested defaults.
The code parses; these are semantic failures, not missing brackets. Repeats and
unrestricted thinking remain necessary before judging consistency.

A fresh unloaded snapshot before GLM showed **23.85 GiB free RAM / 6830 MiB free
VRAM**. Conditional Qwen Q5 and GLM UD-Q6 downloads were queued against explicit
placement estimates and 23.5 GiB / 6800 MiB load gates. Each future load must
pass a new check; these variants are not yet measured fits. Qwen Q5 uses 32K
and 35 CPU expert blocks; GLM UD-Q6 uses 32K and 42 CPU blocks. Differences in
placement/context must be separated from precision effects. Disk-space gates
also remain active; no enormous speculative download bypasses them.

At that same unloaded snapshot, even an optimistic combined resident-weight
budget is only **27.634 GiB** after reserving the existing 2.5 GiB RAM / 400 MiB
VRAM floors. This calculation ignores all runtime, KV/state, compute and staging
buffers, so real capacity is lower. Qwen Q6 (**29.657 GiB**), Kimi Linear Q4
(**27.997 GiB**) and Qwen Coder Next Q4 (**45.196 GiB**) exceed even that bound.
Their current resident profiles are rejected before full download and receive
no quality score. Kimi's architecture is recognized by the pinned runtime; the
obstacle here is current capacity. Disk-paged inference was not benchmarked,
and this is not a claim that these models can never run after freeing apps.
Reassess if unloaded memory changes materially during the remaining campaign.

## Validation and interpretation

Generated code ran only inside Linux/bubblewrap namespaces, with a cleared
environment, separate network/process namespaces and no host home/drive mounts.
Node 24.22.0 and TypeScript 5.9.3 were pinned and verified against their publishers'
SHA256/SHA512 metadata. They are installed under the designated data drive.

The TypeScript/SQLite grader passes a hand-written positive control (6/6 each)
and detects the negative controls (1/6 TypeScript and 2/6 SQLite). Code behavior,
source grounding, test packaging and latency are reported separately. No model
has been promoted on the basis of these small tasks, and editor validation of
the eventual finalists remains part of the campaign.
