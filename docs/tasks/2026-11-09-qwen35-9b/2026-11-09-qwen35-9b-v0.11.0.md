## Decision and rationale

A smaller dense hybrid may give a useful apps-open coding baseline with less
disk traffic than the heavily constrained larger MoE profiles. That is a fit
hypothesis, not evidence that it follows instructions as well as the retained
Qwen3.6 model. Claude staged Q4 and Q5 files on C: on 3 November. New work must
use the owner's E: target; the catalog now points to ordinary E: model paths,
not the old C: junction. Neither file has been relocated or run in this review.

## Results, limits and next action

9November alternative prepared, **not run**:
[full GPU layer weights with CPU q8 KV](../../../profiles/qwen35-9b-q4-gpu-cpukv64.json).
Remove the CPU FFN override; use `--no-kv-offload`,64K/no-context-shift,
b128/u64 and resident4GiB/reserve4.5GiB. From the recorded3November tensor
inventory, moving the1557MiB FFN hot set back to GPU raises estimated device
weights from3304to4861MiB. Moving estimated1088MiB KV to CPU could make
this fit while reducing CPU weight computation. Compute, staging and attention
transfers remain costs, so neither fit nor speed is established. Admission
8.5GiB RAM/11GiB commit/6500MiB free VRAM preserves extra headroom beyond
the estimated weights,450MiB compute,300MiB CUDA overhead and400MiB stop
floor. This directly tests the owner's RAM-KV idea on a smaller dense model;
it cannot inherit either Qwen3.6 scores or the partial-offload estimates.

more predictably than many changing MoE expert pages. Potential cost: a smaller
