## Why this candidate

Claude's 20 October scan ranked LFM2.5 second in its queue. It is a MoE model
with 24B parameters in total and 2.45B active (publisher figures). Its
quantization-aware-distilled (QAD) Q4_0 file is 12.65 GiB, small enough to run
while the owner's applications stay open. The 20 October memory test had shown
that 20 GB-class files thrash on this desktop.

The publisher calls it "best-in-class" for agents and says it is competitive
with Qwen3.6-35B-A3B on agentic and tool-use tasks (LiveClaw 48.09 versus
38.19). Those are publisher claims, not measurements from this lab. The model
would have earned a place by finishing all three suites inside the 1200-second
gate, with a private score close to Qwen Q4's 31/36 at a smaller memory
footprint.

## Results

### Public workflows: 48/60

- **Router, 37/40, in 627.125 s.** Seven turns: six tool turns, each reading
  one file (AGENTS, the router, the v2 rule, the host facts, the contract and
  the code), then the answer. The model correctly left the superseded v1 rule
  unread, and visible text first appeared at 511.97 s. Rubric scores were
  discovery 8, grounding 6, absent facts 6, code 12, behavioural tests 1/3,
  honesty about execution 2 and tool accounting 2/3.
  The isolated contract checks passed 6/6. Its own unit tests ran 4/6: one
  indexes into an int, and another mutates the result and then expects the old
  value. The answer claims the tests were "written to the project" although only
  `read_file` was available. The listed bugs also miss the dropped unknown
  override keys.
- **TypeScript/SQLite, 4/6 and 0/6, in 538.218 s.** It read all six required
  files in the correct order. The TypeScript accepts non-plain objects and the
  non-integer count 1.5, which its own test list says should throw. The
  migration creates `jobs` while the old table still exists, so it aborts with
  `table jobs already exists`. That is one migration failure, not six separately
  observed assertion failures. The migration also omits the composite
  uniqueness it describes. The tests were described in prose only, with no claim
  that they ran.
- **History, 7/8, in 439.157 s.** All six facts and the READY count of 120 were
  correct. Phase 1 reread only `docs/runtime.md` but listed all six paths as
  read in that turn, so the inventory point is lost. The 8,614-token phase-0
  input was processed at 108.7 tok/s.
- Smoke: `READY` with a leading newline, in 1.422 s. The smoke only gates
  transport (see docs/grading.md).

Decode in the long final turns ran at 12.1 to 18.4 tok/s. The public server's
lowest readings were 1.447 GiB free RAM, 8.86 GiB free commit and 1,304 MiB free
VRAM. Peak working set was 13.30 GiB, peak private memory 6.23 GiB and the GPU
peaked at 50 C.

### Private audit: no score

The run reached its deadline at 1200.016 s after four tool turns. Twelve
document ranges were delivered, one of them the entry file supplied by the
harness. Four tool errors occurred: one malformed request, two unavailable
paths (one host path guessed wrongly, one invented report path) and one
oversized range of more than 200 lines that was never requested again in
smaller pieces.

Turn 4 then reasoned for about 874 s without any visible text. At the last
progress save (860.9 s into the turn) it had 10,608 streamed chunks and 28,060
reasoning characters, cycling over the unavailable invented path. The slot held
38,559 tokens when the server cancelled the task, well below the 65,536 context.

During the private interval, free RAM had a median of 3.16 GiB and a minimum of
1.42 GiB, and the process took 3.54 million page faults. Isolated grading of the
public answers ran from 21:56 to 21:57, while this audit was inferring. The
current lab rules keep grading out of inference intervals; the overlap is
recorded here as a changed condition, not as the cause of the loop. Because no
answer was delivered, there is no correctness score and no evidence of a
quantization syntax defect.

**How these grades were produced.** Grading ran automatically 16 s after
collection finished (collect.json 23:39:46, grades.json 23:40:02). It used the
skill's legacy run_candidate path inside WSL bubblewrap, and no source review
came first. The sandbox held, but the review-first rule now in docs/grading.md
was not followed. The frozen grades are kept. A source review made after the
fact on 3 November, without executing anything, is saved separately.

What that review found:

- js_pool's grade of `0/1 exited` came with no parseable grader output. The
  function builds its promise with an executor that discards `resolve` and
  `reject`, then later calls the nonexistent `outerPromise.resolve/reject`. Any
  non-empty call therefore never settles: the evaluator waits forever, Node
  exits silently and the grader writes 0/1. This is a real defect, but 0/1 is an
  artifact of the grader's output format, not one observed assertion failure.
- sql_report fails on a single schema-reading error (one wrong column name), not
  on twenty independent semantic failures.
- On inspection only, without running it, `ttl_lru` would accept a NaN or
  infinite ttl (`ttl <= 0`). The separate NaN-TTL diagnostic used for Flint,
  Qwen and Gemma was not run for LFM.
- On inspection, js_merge replaces arrays instead of merging them by index. It
  therefore avoids the array-to-object defect found in a 24 October Qwen Q4
  answer; this was not executed.

**The interval deadline happened under paging.** For 16 minutes the server
decoded the intervals task at about 4.4 to 5.5 tok/s, with 3-second dips below
0.2 tok/s. Over that window the process took 72,783 page faults and median free
RAM was 2.67 GiB. Only in the last four minutes did decode recover to 13 to
21 tok/s. Later tasks decoded at about 23 tok/s with roughly 6.3 GiB free.

The deadline therefore cannot be blamed on answer length alone. It stays
incomplete and unscored, like any deadline. The server cancelled the task when
the client gave up, so the next task did not wait behind it. The private and
coding server's lowest readings were 1.387 GiB free RAM, 7.60 GiB free commit
and 716 MiB free VRAM, with a 53 C peak GPU temperature.

## Assessment

**Strengths seen here.** The weights are small (12.65 GiB, about 13.3 GiB
working set). Decode is fast: about 23 tok/s on direct coding when the desktop
was not paging, and 12 to 18 tok/s in the public workflows. File discovery was
correct in the router and TypeScript/SQLite workflows, and it handled the
absent facts honestly in the router task. The delivered algorithmic Python and
the SQL window query are correct, and so is the JavaScript deep merge.

**Weaknesses seen here.**

- The instruction-heavy private audit fell into a loop after an invented path.
- Delivered code had small but fatal slips: a wrong column name, a missing
  import and a strict-mode definite-assignment error.
- One promise implementation can never settle.
- It overclaimed file reads and claimed to have written test files.
- Its own tests were weak.

The good public router score did not predict reliability on the private
instructions. This repeats the lesson in the current comparison.

**Suitable work.** Supervised, self-contained functions whose output is checked
independently. It is not suited to unattended work that depends on many
instruction files, or to the owner's default assistant.

**Comparison limits.** The three suites used different effective samplers
(above). The desktop paged during the private audit and the intervals task. The
driver was 617.42, against 621.01 in later trials. There is no matched Qwen run
of the twelve coding tasks from the same day. Treat this as one seed per
component, not as a controlled ranking.

**Recommendation.** It stays retired. An unchanged retry would add nothing.
Any return needs a separately labelled control with a concrete reason. One
option is the publisher's own evaluation settings ("other evals: temperature
0.6, max output tokens 32768" on the base card). Another is a private audit
that actually applies the publisher's 1.05 repetition penalty, each with fresh
seeds and an apps-closed memory window. Neither has been run.
