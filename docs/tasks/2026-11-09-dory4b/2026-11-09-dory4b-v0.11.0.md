# Dory1.0-4B: prepared looped-model comparison

9 November 2026 · v0.11.0 · **runtime qualification pending; no inference**

## Decision and rationale

Dory's looped architecture is an interesting small-weight reasoning candidate.
Loop count changes compute and cache requirements; it is not equivalent to a
Qwen thinking-effort string. Claude staged the Q5 file on C: but did not finish
full hash verification. A compatible runtime and an E: copy are prerequisites.
The ordinary b12069 runtime has not established support for this architecture.

The embedded template uses `medium_effort` and `truncate_history_thinking`;
the prepared setting is not proof that generic `preserve_thinking` works.
Template marker checks, architecture support and pinned-runtime compatibility
controls must precede load. Two versus four loops must be reported separately.

9 November primary-source refresh: [upstream PR30306](https://github.com/ggml-org/llama.cpp/pull/30306)
is still draft. Its author states that `last_loop` changes predictions and
depends on prefill chunking. A later contributor also reports chunk-sensitive
differences in `per_loop`; that is an unreplicated report, not a local finding.
The [publisher's current CUDA example](https://huggingface.co/nvidia/NVIDIA-Nemotron-Labs-Dory1.0-4B-GGUF)
starts at 4K context, f16 KV, flash attention off and two loops. Therefore the
prepared 64K/q8/flash-on profile above is a later experiment, not the first
supported smoke recipe. Qualify the documented small-context configuration
before testing those extra settings. Last-loop cache savings must not be
presented as an output-equivalent optimization.

Further source review on 9 November found that the publisher's pinned
`98a74c9` predates two relevant fixes. The
[scale-placement change](https://github.com/brianchmielNV/llama.cpp/commit/9e2f3be)
addresses BF16 scale tensors being placed on CPU despite GPU execution;
the later [placement/KV-device correction](https://github.com/brianchmielNV/llama.cpp/commit/3834b4a)
separates physical blocks from repeated virtual layers. The PR includes a
contributor's substantial speed gain on different hardware, not a local
measurement. Current head `1c3cdd2` also merges later upstream work, so using
it would be a separately pinned runtime experiment. The
[fork release page](https://github.com/brianchmielNV/llama.cpp/releases)
has no published releases. A stock download is therefore not a qualified
substitute for a reviewed build. Preserve the original proposed pin as
provenance, and review these fixes before choosing the actual Windows build.

## Results, pros/cons and remaining work

No measured latency, memory consumption, file-read score, coding grade or
editor pass exists. Low weight size is promising, but a looped cache and repeated
compute can erase that advantage. Reducing loops may also affect answer quality;
no claim about its superiority to the retained Qwen is justified.

First verify artifact identity and supported runtime behavior, then qualify
a bounded greeting. Only after that should the fixed file/coding suites compare
loop counts, effort and history preservation. Preserve default-loop and
reduced-loop results independently. An unsupported architecture is a runtime
gap, not a failed reasoning score. No production change or deletion occurred.

Owner scope: preserve a model-wise record of Claude's preparation and identify
what actually remains before an apps-open experiment can be called tested.
