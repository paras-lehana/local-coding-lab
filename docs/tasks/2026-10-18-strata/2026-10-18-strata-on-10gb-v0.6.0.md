## Why full Flash-Next was selected

The second candidate is the full GSQ-RCO IQ3_XXS Flash-Next, not the earlier
dense Qwen3.8 and not Strata's pruned Coder variant. This exercises Strata's
separate SSD/RAM/GPU expert tiers and native xhigh reasoning template. Those
features make it a relevant experiment; neither the larger parameter count
nor the quantization name establishes better coding quality.

The frozen initial plan is32K/int8 KV,10GiB resident experts,1200MiB VRAM
reserve,256-token prefill chunks and7CPU workers. MTP and suffix speculation
are disabled to measure the base path first. Native xhigh has a2048-token
reasoning ceiling per turn; it is not unlimited thinking. Sampling uses the
artifact's temperature1.0, unlike the Qwen control's0.6. The same public
router/history/TS-SQL questions, sources, output limit and whole-case deadline
are frozen before inference. A Flash/Qwen timing difference consequently
changes both the model and its practical configuration, not just the engine.

Direct GGUF expert views can use unbuffered reads and avoid a second roughly
40GiB expert copy. The resident budget is incompatible with elastic KV growth;
the longer-context follow-up therefore used the separate KV streaming mode.
The measured51Kinput and diagnostic recall are described above; a larger
context setting alone does not count as a populated-context test.
Published12GB community runs use different RAM budgets and acceleration, so
their speeds are reference material rather than predictions for this machine.

## Memory and context: these are different engine paths

Our production llama.cpp profile uses128K context and CPU q8KV. Strata's
Qwen3.6 path keeps fp32 attention KV on the GPU and copies all routed expert
weights into a host arena, including experts also cached on the GPU. Increasing
its GPU expert budget therefore does not subtract the same amount from that
host arena. Flash-Next RAM-budget or KV-streaming flags are not Qwen3.6 controls.

Flash-Next has a separate bounded host-resident expert tier plus an SSD-backed
remainder. Its `--kv-resident` can keep part of KV on GPU and the rest in RAM.
The51K trial above measures real RAM-backed KV reads, but does not establish
full128K accuracy or that all editor instructions are sent and followed.

Strata's API does not forward `preserve_thinking` from chat-template kwargs.
The copied Qwen tokenizer template explicitly sets it true for this experiment,
matching the production template setting. Preserve the original and effective
template hashes in private evidence. Also, Strata reasoning budget0 means
unlimited, not thinking disabled. A native Qwen on/off template is not an
independent ultra/high/medium reasoning-effort control.

## What this changes in the recommendation

Strata is viable on the actual10GB card; it does not need a fictitious12GB
gate removed. The useful fork work is compatibility and Windows residency,
not changing a minimum-VRAM constant. For the installed Qwen Q4, three complete
32K workflows are faster than the same-day llama profiles, but require more
memory headroom and include a failed SQL migration. The different execution
and output paths mean one bad migration is not proof that Strata universally
reduces quality; it is sufficient reason not to claim an upgrade from these
single samples.

Full Flash-Next adds a much larger SSD-backed expert/embedding workload and
different weights/quantization. MTP consumes cache space; increasing resident
RAM improves measured throughput, but the tested coding answers remain too
slow to finish within the chosen20minute budget. This does not establish that
IQ3 causes syntax errors: no incomplete response has a syntax or quality score.
Nor does it show that the pruned Coder variant would behave like the full model.

Keep the existing llama.cpp Qwen Q4/128K CPUq8KV setup as the working endpoint.
Use this fork as an experimental32K alternative only, with its measured guards.
If developing it further, CPU/quantized KV support for the Qwen engine is more
relevant to this owner's long-file workflow than maximizing a GPU usage meter.
That is a proposed engineering direction, not a completed or proven port.
