## Initial measured profile and next control

Initial32GPU/32K/resident2GiB load becomes ready in14.875s. Cold hi completes
in112.875s, first visible105.437s,135output tokens,1.219decode tokens/s. Repeated
hi completes120.844s, first visible112.938s,145output tokens,1.205tokens/s;
12of17prompt tokens reused. Both complete, but this is poor greeting latency.

The loader reports4573.66MiB GPU model buffers; q8 KV272.00MiB global plus
212.50MiB sliding-window. Of that484.50MiB total,147.69MiB is CPU and336.81MiB
GPU. Rotation/compute buffers are additional. This is allocation at startup,
not a proof of dynamically growing cache or successful long-context recall.
Process residency stays near2GiB, with more than12GiB system RAM still free.
The cap may be restrictive; raw page-fault counts include soft faults and do
not establish equivalent SSD reads.

After both greetings, an explicit owned stop ended this profile to compare a
3GiB cap before collecting coding. The first merge request raced that stop and
returned no answer: it is intentionally interrupted and unscored, not an
observed model bug. The original collector's failed/incomplete receipt remains
unchanged beside the separate intentional-transition receipt. Native cleanup
is requested_stop; expanded hardware query finds no new event.

The resident3 profile changes only residency2to3GiB and the corresponding admission
gate7to8GiB, retaining the5GiB reserve. A separate prepared capacity combination
uses36GPU layers and all-CPU q8 KV with3GiB residency. That combination changes
more than one variable and is not a single-factor speed claim.

Resident3 becomes ready in12.312s with14.331GiB available RAM,30.926GiB

This roughly sixfold observed decode gain is a paired sample,

setting.

The return-to-resident2 control finishes normally at02:18IST:110.359/117.406s

The CPU32 alias assertion checks only the overwritten base list, so it would
miss a result aliased to the patch list. Independent checks cover that gap.
CPU34's own test wrongly expects a key added to the input after merging to
appear in the isolated result. The isolated runner reproduces that exact
assertion failure while all five implementation groups pass. This is a
model-written test defect, not a syntax or merge-implementation failure.

Moving KV to RAM gains measured GPU headroom, but more GPU layers did not yield
a clear speed gain. Generated text and token counts differ at the same seed,
so wall time alone is not a fixed-output throughput comparison. Keep32GPU/
mixedKV/resident3 as the short-context performance reference; CPU32 is a
capacity candidate for longer context, not a demonstrated accuracy upgrade.
No long-context recall test or file audit is complete on these profiles.

Potential advantages: smaller disk/RAM footprint, native thinking/tool support,
official QAT. Potential limits: fewer parameters, some weights still on CPU,
native256K is not yet served or tested here, finite accuracy remains unknown.
The narrow merge diagnostic compiles/executes and passes behavior checks;
citation, multi-file, long-history and full coding coverage remain untested.
Earlier26B/31B scores belong to their own models/profiles and are not transferred.
