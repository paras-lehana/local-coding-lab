# Review of the Gemini research

Reviewed 14 October 2026 against the retained local measurements, pinned runtime
help/source, publisher model metadata and the primary sources linked below.
The [source text](../raw/2026-10-14-gemini/report.txt) is preserved separately.

## What changes our plan

Keep Qwen Q4 as the measured reference. Gemma 4 26B QAT is the next smaller
candidate; GLM UD-Q4_K_XL at 32K is a more realistic tight-memory challenger than
the earlier Q5 proposal. Test all-non-expert GPU placement as a **single change**
when host RAM allows. These are test priorities, not quality rankings.

The research supports retaining q8 KV for now. Our current Qwen attention cache
is already small, so moving it to RAM is unlikely to solve the dominant host
memory/CPU-compute problem. It remains a useful later controlled experiment.

## Claim audit

| Source claim | Review | Consequence |
|---|---|---|
| Qwen is the best local measured reference | Supported within our limited completed tests | Retain reports/weights; do not declare universal superiority |
| Qwen is currently a reliably fitting production assistant | Stale/incomplete | Subsequent memory stops left it unloaded; inspect live headroom each time |
| Proposed configuration 1.5 will deliver 20–28 tok/s and finish the audit in 620–780s | Unmeasured estimate | Do not publish as a result or promise |
| Temperature 0.35, min-p 0.02, larger batches, all-attention GPU placement and 1536 MiB prompt cache should change together | Confounded and adds host memory | Test placement, sampling and caching separately; keep cache-ram 0 initially |
| The remaining coding errors do not stem from Q4 quantization | Causal claim not established | Need a matched Q4/Q5 experiment; the current data neither proves nor excludes quantization effects |
| Same small-task scores show zero Q8 advantage | Too broad | A few identical passes do not prove equivalence on harder tasks |
| Google Gemma QAT had malformed vocabulary exports | Supported historical report and publisher fix | Verify the exact revision; do not assume every current Google file is broken |
| ggml-org QAT guarantees immunity | Guarantee unsupported | It is an alternate artifact requiring its own hash/load/template tests |
| GLM non-UD quants must not be used with OpenHands | Not found in the current checked publisher guide | Prefer smaller UD for memory/test coverage, not an unverified prohibition |
| GLM Q5 guarantees a memory shutdown | Too strong | Device placement, compute/KV buffers and current headroom decide fit |
| Native preserved thinking guarantees file memory | Unsupported | Validate client history transport, explicit reads, stale-file updates and actual recall |
| Native 128K context implies all instructions/files survive | Unsupported | Client truncation and retrieval quality remain separate |

The raw research uses an older ~21 GiB reclaimable-RAM estimate. Later local
snapshots fell to 16–18 GiB after unloading. During repository preparation a
read-only snapshot showed 23.25 GiB free RAM and 7150 MiB free VRAM. These are
different times, not contradictions or guaranteed future capacity.

## Primary-source checks that matter

The publisher acknowledged and repaired malformed Google Gemma GGUFs in July.
A subsequent report names revision `d1c082be9cf3c8a514acf63b8761f4b41935842e`,
the exact revision in our catalog. That is a stronger basis than applying an
old bug report to every export. The research's Google byte count is also 2144
bytes smaller than the current pinned metadata: our catalog records
**14,439,363,584 bytes**. [Publisher discussion](https://huggingface.co/google/gemma-4-26B-A4B-it-qat-q4_0-gguf/discussions/10).

The upstream issue contains reports for multiple Gemma variants and a maintainer
test of the ggml-org QAT alternative. It supports a historical compatibility
risk, not a guarantee for a different future binary/template combination.
[Runtime issue #25739](https://github.com/ggml-org/llama.cpp/issues/25739).

Unsloth's current GLM guide documents a past router-scoring fix, tool-call
sampling of temperature 0.7/top-p 1.0, repeat penalty 1.0, min-p 0.01, and uses
UD-Q4_K_XL in examples. Its visible compatibility warning concerns Ollama.
We did not find the claimed blanket non-UD/OpenHands prohibition there.
[Publisher guide](https://unsloth.ai/docs/models/tutorials/glm-4.7-flash.md).

Our pinned GLM UD-Q4_K_XL artifact is **17,520,169,312 bytes (~16.317 GiB)**.
Publisher LFS size/hash and revision were checked through the Hugging Face API.
Its actual MLA/compute allocations and q8-cache stability remain local-test
questions. [Pinned artifact files](https://huggingface.co/unsloth/GLM-4.7-Flash-GGUF/tree/0d32489ecb9db6d2a4fc93bd27ef01519f95474d).

## Not yet verified

Gemma's current embedded tool DSL/template round trips, GLM's local cache layout
and repetition behavior, proposed expert-cache hit rates, independent benchmark
figures quoted only through numbered placeholders, and the source's per-model
latency estimates remain unverified. Nothing in this document authorizes
executing its proposed shell commands without normal artifact/profile checks.

The source's proposed 40-point extended benchmark is useful inspiration. Our
new public router-v1 rubric is a separate design; it currently lacks the source's
stale-file, transient-tool-failure and long-history stages. No historical score
has been relabeled as a result on this public corpus.
