# Review of the Gemini research

Reviewed 14 October 2026 against the retained local measurements, pinned runtime
help/source, publisher model metadata and the primary sources linked below.
The [source text](../raw/2026-10-14-gemini/report.txt) is preserved separately.

## What changes our plan

Keep Qwen Q4 as the measured reference. Gemma 4 26B QAT is the next smaller
candidate; GLM UD-Q4_K_XL at 32K is a more realistic tight-memory challenger than
the earlier Q5 proposal. Test all-non-expert GPU placement as a **single change**
when host RAM allows. These are test priorities, not quality rankings.

The research supports retaining q8 KV for now. Our current Qwen attention cache
is already small, so moving it to RAM is unlikely to solve the dominant host
memory/CPU-compute problem. It remains a useful later controlled experiment.

The raw research uses an older ~21 GiB reclaimable-RAM estimate. Later local
snapshots fell to 16–18 GiB after unloading. During repository preparation a
read-only snapshot showed 23.25 GiB free RAM and 7150 MiB free VRAM. These are
different times, not contradictions or guaranteed future capacity.

## Primary-source checks that matter

The publisher acknowledged and repaired malformed Google Gemma GGUFs in July.
A subsequent report names revision `d1c082be9cf3c8a514acf63b8761f4b41935842e`,
the exact revision in our catalog. That is a stronger basis than applying an
old bug report to every export. The research's Google byte count is also 2144
bytes smaller than the current pinned metadata: our catalog records
**14,439,363,584 bytes**. [Publisher discussion](https://huggingface.co/google/gemma-4-26B-A4B-it-qat-q4_0-gguf/discussions/10).

The upstream issue contains reports for multiple Gemma variants and a maintainer
test of the ggml-org QAT alternative. It supports a historical compatibility
risk, not a guarantee for a different future binary/template combination.
[Runtime issue #25739](https://github.com/ggml-org/llama.cpp/issues/25739).

Unsloth's current GLM guide documents a past router-scoring fix, tool-call
sampling of temperature 0.7/top-p 1.0, repeat penalty 1.0, min-p 0.01, and uses
UD-Q4_K_XL in examples. Its visible compatibility warning concerns Ollama.
We did not find the claimed blanket non-UD/OpenHands prohibition there.
[Publisher guide](https://unsloth.ai/docs/models/tutorials/glm-4.7-flash.md).

Our pinned GLM UD-Q4_K_XL artifact is **17,520,169,312 bytes (~16.317 GiB)**.
Publisher LFS size/hash and revision were checked through the Hugging Face API.
Its actual MLA/compute allocations and q8-cache stability remain local-test
questions. [Pinned artifact files](https://huggingface.co/unsloth/GLM-4.7-Flash-GGUF/tree/0d32489ecb9db6d2a4fc93bd27ef01519f95474d).

## 15 October measured corrections

The pinned Gemma 26B header has **25 sliding-window and five global-attention
blocks**, rather than the research's 26/four split. Its actual 32K q8 allocation
is 340 MiB global plus 132.81 MiB sliding-window cache. Runtime allocation also
includes padding beyond the nominal sliding window; the original 64K estimate
must not be copied into a launch-memory promise. See the
[measured campaign](../../reports/2026-10-15-campaign.md).

Kimi's official config and the inspected GGUF agree on **27 blocks, 256 routed
experts and eight selected experts**, with 20 KDA and seven full-attention blocks.
The research's 36-block/128-expert description is incorrect for this checkpoint.
Its native maximum is 1,048,576 tokens; that is not the context deployed locally.
[Pinned official config](https://huggingface.co/moonshotai/Kimi-Linear-48B-A3B-Instruct/blob/e1df551a447157d4658b573f9a695d57658590e9/config.json).

GLM Q5 subsequently loaded with apps open: 5.57 GiB dedicated process VRAM,
16034 MiB host model buffers and a 899 MiB q8 MLA cache at 32K. Thus the source's
guaranteed shutdown claim does not describe this measured placement/headroom.
It is still being quality-tested. GLM Q4's unrestricted reasoning hit its output
limit; whether cache precision affects that behavior remains an experiment.

## Remaining verification after the campaign began

### 16 October: measured context allocation and retention

The new [context experiment](../../reports/2026-10-16-context-growth.json)
supports the report's small Qwen attention-cache estimate: 680 MiB q8 at 64K,
1360 MiB at 128K, with 62.81 MiB recurrent state in both configurations. Within
one configured capacity the cache buffers remain allocated while token
occupancy grows. Resident RAM is not a token counter.

At 119,943 input tokens, all-CPU KV/state completed in 733.063s and the default
mixed GPU/CPU placement in 610.016s. Both recovered all five facts but violated
the plain-JSON request with a code fence. Both recovered the inline file update
and earlier facts in a follow-up; both returned UNKNOWN when history was
omitted. This supports cache reuse and the importance of client-delivered
history, not the report's stronger claim that preserved thinking guarantees
file memory. These probes explicitly disabled reasoning; they are memory
diagnostics, not coding-quality scores.

The report's q8-to-q4 saving also needs block overhead. At the pinned runtime,
q8_0 stores34bytes per32values and q4_0 stores18, including each half-precision
scale. For Qwen's10attention layers/two KV heads/256-dimensional K and V at
65,536tokens, that gives680MiB q8 versus360MiB q4: a320MiB saving, not340.
The comparable f16 payload is1280MiB. At128K the q8-to-q4 saving would be640MiB.
These are source-derived attention-payload calculations; no q4 cache load,
compatibility or recall-quality test is claimed. Recurrent state, checkpoints,
alignment and compute buffers are separate. Retain q8 for the precision pair.
The block definitions were inspected in the local checkout at the pinned commit;
the web fetch of that file timed out.
[Pinned block layouts](https://github.com/ggml-org/llama.cpp/blob/b2f036c0f138414dedc987446f1d9d802f920275/ggml/src/ggml-common.h#L194).

The report's blanket claim that RAM-only KV becomes non-pageable `CUDA_Host`
memory is incorrect for the pinned runtime. With offload disabled, the checked
KV and recurrent-state constructors select `ggml_backend_cpu_buffer_type()`;
that backend uses the ordinary aligned allocator. The measured CPU64 log labels
680MiB KV and62.81MiB recurrent state as `CPU`, while separately labeling host
weight/compute buffers `CUDA_Host`. Do not infer pinning from the presence of a
CUDA device or combine these allocations into a single cache figure.
[Pinned cache constructor](https://github.com/ggml-org/llama.cpp/blob/b2f036c0f138414dedc987446f1d9d802f920275/src/llama-kv-cache.cpp#L214),
[pinned CPU allocator](https://github.com/ggml-org/llama.cpp/blob/b2f036c0f138414dedc987446f1d9d802f920275/ggml/src/ggml-backend.cpp#L2542).

The owner also relaxed the former 20-minute practical limit. Coder-Next 80B,
dense Gemma 31 and Qwen Q6 are reopened for explicit longer trials. Their former
capacity/latency exclusions cannot be reused as quality verdicts. The pinned
loader avoids device host-weight buffers when mmap is enabled; this makes
file-backed residency an experiment worth attempting. Whether storage paging
is usable must be measured, not inferred from a successful load. See the
[expanded task report](../../docs/tasks/2026-10-16-memory-and-candidate-expansion/2026-10-16-memory-context-and-expanded-model-tests-v0.4.0.md).

### Outstanding source claims

The16October publisher-card recheck finds a benchmark attribution problem:
Qwen's official table gives SWE-bench Verified73.4 to Qwen3.6-35B-A3B and75.0
to Qwen3.5-27B. It does not establish the supplied report's75.0-thinking versus
73.4-non-thinking comparison for Qwen3.6. The table uses an internal agent
scaffold and200K context, so its score is not a measurement of our quantized
64K local setup. The cited IFBench64.4 and telecom95.3 figures remain unverified
from that card. They are excluded from our measured ranking.
[Pinned Qwen publisher card](https://huggingface.co/Qwen/Qwen3.6-35B-A3B/blob/995ad96eacd98c81ed38be0c5b274b04031597b0/README.md).

GLM's publisher does report SWE-bench Verified59.2 and tau2-Bench79.5, but its
table labels the latter as tau2 overall, not explicitly telecom-only. Its
evaluation notes describe domain fixes and task-specific sampling. Cross-card
numbers are background evidence, not a controlled local comparison.
[Pinned GLM publisher card](https://huggingface.co/zai-org/GLM-4.7-Flash/blob/7dd20894a642a0aa287e9827cb1a1f7f91386b67/README.md).

That correction suggests dense Qwen3.5-27B as a later hypothesis, after the
requested matrix. Its official overview specifies64 blocks with dense FFNs,
48 DeltaNet and16 full-attention blocks; four KV heads differ from the current
35B model's two. Shared family naming does not justify copying the current
cache estimate. A GGUF repository exists, but no artifact has been selected,
downloaded or locally tested here. The publisher coding result motivates a
test, not a recommendation to replace a measured local setup.
[Qwen27B overview](https://huggingface.co/Qwen/Qwen3.5-27B#model-overview),
[available GGUF repository](https://huggingface.co/unsloth/Qwen3.5-27B-GGUF).

The MTP proposal is worth a conditional follow-up, not a guaranteed dense-model
speedup. Google's31B assistant has four small layers and shares the target KV;
the pinned runtime contains the Gemma assistant and `draft-mtp` paths. The
upstream support thread includes both improvements and zero-acceptance
slowdowns under different placements. Those are not measurements of this
CPU-heavy workstation. A future trial must record accepted draft tokens,
whole-request time, actual memory, and correctness rather than assume2x.
[Publisher assistant](https://huggingface.co/google/gemma-4-31B-it-assistant),
[upstream implementation and measurements](https://github.com/ggml-org/llama.cpp/pull/23398).

The new dense history test identifies another optimization that the generic
"keep KV in RAM" advice misses. The default Gemma template removes older tool
reasoning when the next user message arrives. Actual rendered/tokenized requests
then share only137 leading tokens, and the active server logs full prompt
reprocessing because its retained SWA checkpoint cannot restore that prefix.
With `preserve_thinking=true`, the same requests share10,021 leading tokens,
at341 additional follow-up tokens (counts exclude BOS). This setting has only
been rendered/tokenized; no speed or quality improvement is claimed. Retaining
thoughts consumes context, and editor clients must actually resend the relevant
fields. More checkpoint RAM alone cannot recover a changed early prompt prefix.
The current profile and native benchmark requests remain unchanged.

There is also a version-specific caveat: the zero-free-device-memory split fix
was merged on14October, after our12October b11562 pin. Our checked source still
divides by `split_sum` without that fallback. This applies when device-reported
free memory is zero while another model is loaded; it does not diagnose the
current1.2tokens/s dense run or any historical system restart. Do not fill the
GPU blindly to add a draft model or change the runtime midway through the
frozen Q4/Q6 comparison. First finish the native-quality trials; a separately
identified CPU-draft/updated-runtime control can follow if dense quality merits
it. No draft artifact or MTP inference has been run in this expansion.
[Merged fix #29677](https://github.com/ggml-org/llama.cpp/pull/29677),
[checked pinned split calculation](https://github.com/ggml-org/llama.cpp/blob/b2f036c0f138414dedc987446f1d9d802f920275/src/llama-model.cpp#L1638).

CPU weight repacking is another conditional dense-model experiment. The pinned
backend has an AVX2 Q4_0 repacking path, but `CPU_REPACK` allocates ordinary CPU
buffers; it is not the existing file-backed weight mapping. Host-buffer
preference can also bypass that selection, so removing `--no-repack` alone is
not evidence that repacking occurred. A future trial must confirm the actual
loader buffer type, check additional commit headroom and compare complete
requests at unchanged sampling. It may improve CPU kernels without improving
coding accuracy; no speedup or fit is claimed, and no repacking trial has run.
The current mapped experiments deliberately keep repacking disabled.
[Pinned CPU repacking implementation](https://github.com/ggml-org/llama.cpp/blob/b2f036c0f138414dedc987446f1d9d802f920275/ggml/src/ggml-cpu/repack.cpp#L4974),
[pinned buffer selection](https://github.com/ggml-org/llama.cpp/blob/b2f036c0f138414dedc987446f1d9d802f920275/src/llama-model-loader.cpp#L1236).

The16October80B experiment also overturns a blanket apps-open capacity
exclusion. Stock Windows mmap loading caused a severe physical-memory/commit
dip despite a working-set cap. An explicitly identified, same-commit runtime
variant disabling initial mmap prefetch then loaded and ran the model with
apps open. This does not make45.20GiB of weights resident in14GiB: repeated
file-backed paging remains expensive. The completed recovery audit averaged
6.27uncached input tokens/s and ended at its16-tool-turn limit after67m55s,
repeatedly reading incorrect paths without a final answer. Thus this particular
profile is rejected on measured workflow evidence, not merely file size.
[Runtime controls](../../reports/2026-10-16-runtime-controls.json),
[80B measurements](../../reports/2026-10-16-coder-next.json).

The supplied generic `preserve_thinking=true` advice also needs model-specific
checking. Gemma31's exact pinned template preserves reasoning during the current
tool sequence even with this option false; true additionally retains older
user-turn tool reasoning. Offline synthetic markers confirm that both options
retain previously delivered source contents. The public dense trial therefore
uses the publisher's history policy and sampling temperature1.0. The actual
server's `/apply-template` route subsequently passed the same marker checks,
including OpenAI-compatible string tool arguments without doubled braces.
These synthetic checks establish server rendering, not completed editor or
model-quality behavior. [Template evidence](../../reports/2026-10-16-gemma-template.json),
[publisher best practices](https://huggingface.co/google/gemma-4-31B-it#best-practices).

The completed dense31B quality tests do not establish a workflow upgrade.
Public Python passes6/6, TypeScript5/6, and SQLite fails on foreign keys.
The private merge helper also passes6/6, but the whole instruction audit is26/36
after2h00m34s: required guidance and accurate read accounting remain deficient.
The private client overrides top_k64/preservationfalse with20/true, so this is
not a publisher-sampling private result. Longer waiting reveals actual strengths
and defects; it cannot be replaced by an assumption that dense means more
reliable instruction following. [Reviewed measurements](../../reports/2026-10-16-gemma31.json).

The dense placement follow-up further limits the generic offload advice.
At unchanged32K CPU-KV capacity, moving14complete blocks plus output ontoGPU
improves short generation from1.18to1.56tokens/s, while8K whole latency remains
about7.7minutes. Moving525MiB KV ontoGPU then leaves short latency unchanged
and the longer run stops below400MiB freeVRAM; its incomplete answer is unscored.
The extra consumer is not attributed. These shared-desktop diagnostics support
measuring whole tasks and leaving margin; filling moreVRAM is not itself a
quality or speed result. [Placement evidence](../../reports/2026-10-16-dense-placement.json).

Finally, the proposed Q6 test is a mixed-precision artifact comparison. The
inspected Q4 routed-expert tensors include Q4_K, Q5_K and Q6_K; Q6 uses Q6_K and
Q8_0. Most non-expert tensors are already Q8_0 in Q4. The extra9.04GiB therefore
mainly increases expert precision rather than upgrading every tensor uniformly.
Matched prompts, sampling and runtime placement are frozen before collection;
their quality results remain pending. [Header evidence](../../reports/2026-10-16-quantization-headers.json).

Gemma/GLM native tool continuation and local cache allocations now have evidence
in the campaign report. Expert-cache hit rates, independent benchmark figures
quoted only through numbered placeholders, and the source's per-model latency
estimates still require validation. Nothing in this document authorizes
executing its proposed shell commands without normal artifact/profile checks.

The source's proposed 40-point extended benchmark is useful inspiration. Our
new public router-v1 rubric is a separate design. Separate history scenarios now
cover changed files and retained beginning/middle/end facts, with an unavailable
ledger tool response if requested. Successful memory answers that never attempt
that read do not establish transient-error recovery. No historical score has
been relabeled as a result on this public corpus.
