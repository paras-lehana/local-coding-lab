Audit of the Prior Assistant's Analysis: Five Technical Corrections

First, the prior analysis overestimated the coding strength of GLM-4.7-Flash while overlooking its severe runtime memory and KV cache liabilities in llama.cpp. Released in January 2026 (zai-org/GLM-4.7-Flash, 31.2B total / ~3.0–3.6B active parameters, 47 layers, 64 total experts with 4 routed active), GLM-4.7-Flash predates the April 2026 release of Qwen3.6-35B-A3B. On standardized agentic evaluations, GLM-4.7-Flash scores 59.2% on SWE-bench Verified and 79.5% on τ2\tau^2τ2-Bench, trailing Qwen3.6-35B-A3B's 73.4%–75.0% on SWE-bench Verified and 95.3% on τ2\tau^2τ2-Bench Telecom by a wide margin. More critically, the prior assistant evaluated GLM-4.7-Flash Q5_K_M strictly by its 19.939 GiB (21.4 GB) static weight file. Unlike Qwen3.6-35B-A3B, which employs Gated DeltaNet linear attention in 30 of its 40 layers and full Gated Attention in only 10 layers (keeping its 64K q8_0 attention KV cache to 680 MiB plus 62.81 MiB of recurrent state), GLM-4.7-Flash uses Multi-head Latent Attention (MLA) across all 47 layers. When MLA latent vectors are unmerged or fall back to standard 20-head Multi-Head Attention in llama.cpp, the KV cache consumes 0.72–0.96 MB per token (~45–60 GiB at 64K context); even when compressed MLA kernels are active (~54 KB/token in FP16 or ~28.7 KB/token in q8_0), 64K context requires ~1.8 GiB of KV cache alongside multi-gigabyte attention compute buffers that cause out-of-memory failures and steep prefill degradation as context depth increases. In addition, Unsloth's documentation explicitly warns against running standard non-UD quantizations (Q4_K_M, Q5_K_M) of GLM-4.7-Flash with coding agents such as OpenHands, and community reports document // // // token repetition loops under q8_0 KV caching, making UD-Q4_K_XL (17.5 GB / ~16.30 GiB) at a 32K context limit the only safe apps-open test configuration. Meanwhile, newer Z.ai releases (GLM-5.1, GLM-5.2, GLM-5.3-Flash at 321B parameters, and GLM-5.3 at 753B parameters) are datacenter-scale models that cannot run on a 64 GB workstation.

Second, while the prior assistant correctly noted that Gemma 4 26B-A4B (google/gemma-4-26B-A4B-it-qat-q4_0-gguf, 25.2B total / 3.8B active parameters, 13.448 GiB text GGUF) offers generous memory headroom and Quantization-Aware Training (QAT), it omitted three critical integration bugs affecting llama.cpp on Windows. In July 2026, Google's official Gemma 4 QAT GGUF exports (both 26B-A4B and 31B) triggered a fatal vocabulary assertion crash upon loading in llama.cpp Windows CUDA builds (GGML_ASSERT(id_to_token.size() == token_to_id.size()), Issue #25739) because the 262,144-token vocabulary contained three duplicate visible token strings (//, #, and a whitespace entry). Although Google subsequently pushed a repository update (discussions/10) and the llama.cpp maintainers published a verified working QAT build at ggml-org/gemma-4-26B-A4B-it-GGUF (14,618,145,824 bytes / 13.614 GiB, which stores token_embd.weight in Q8_0 rather than Google's Q6_K or Unsloth's Q4_0), two chat-template hazards remain. Specifically, Gemma 4's upstream Jinja template defaults enable_thinking to False, meaning that unless <|think|> is injected into the first system turn or --chat-template-kwargs "{\"enable_thinking\": true}" is forced at the server level, thinking stays silently disabled. Worse, Gemma 4 relies on a custom non-JSON tool-calling DSL (declaration:fn{...}, call:fn{...}); when OpenAI-compatible clients serialize tool_call.arguments as a JSON string across multi-turn history, the unpatched template wraps the payload in double braces (call:fn{{"path":"..."}}) and historically stripped prior-turn <|channel>thought blocks, causing tool arguments to collapse to {} after two to three tool rounds.

Third, Qwen3.6-35B-A3B is uniquely engineered for the exact constraints of the operator's repository workflow. Built on direct feedback for agentic coding, Qwen3.6-35B-A3B natively introduces preserve_thinking—retaining <think>...</think> blocks from all preceding turns in multi-turn conversations so the model does not lose track of previously read instruction routers or file dependencies across sequential tool calls. Independent Artificial Analysis benchmarks demonstrate that activating thinking mode on Qwen3.6-35B-A3B elevates instruction following (IFBench) by +28.2 percentage points (from 36.2% to 64.4%), τ2\tau^2τ2-Bench Telecom from 85.1% to 95.3%, long-context retrieval (AA-LCR) from 64.3% to 71.7%, Terminal-Bench Hard from 25.8% to 34.8%, and the AA-Omniscience Non-Hallucination Rate from 7.9% to 49.5%. Its local Configuration 1.3 audit score of 31/36 (86.1%) in 863.89 seconds (14m 24s) already satisfies the 20-minute (1,200-second) end-to-end deadline with more than five minutes of margin.

Fourth, the remaining 5/36 errors on the local audit (mutable-object aliasing in Python and incomplete coverage of linked instruction files) do not stem from 4-bit weight compression in UD-Q4_K_M, and loading Qwen3.6-35B-A3B UD-Q5_K_M (24.639 GiB) with normal applications open would add 4.025 GiB of CPU weights, immediately breaching the 2.5 GiB physical RAM watchdog floor. Instead, the local comparison between temperature 0.6 (31/36) and temperature 1.0 (26/36, which introduced incomplete nested defaults, aliasing, and dropped local-only keys) indicates that sampling stochasticity and server layer/cache configuration are the primary levers. Tightening temperature to 0.35 with --min-p 0.02, shifting all 40 non-expert attention/DeltaNet layers to the GPU via -ngl all --cpu-moe, and bounding llama-server's RAM prompt cache (--cache-ram 1536) directly target those failure modes without risking an out-of-memory shutdown.

Fifth, the conditional dense candidate (Gemma 4 31B IT QAT Q4_0, 16.439 GiB) faces a fundamental hardware bandwidth barrier on dual-channel DDR4-2800. With only 5.5–6.0 GiB of usable process VRAM, at least ~12.1 GiB of the 30.7B dense model's weights must reside in system RAM. Whereas a 35B-A3B MoE activates only 3B parameters per token (reading ~1.5–1.8 GiB of CPU weights per generated token), a 30.7B dense model activates every parameter on every token, forcing the CPU to stream ~12.1 GiB from DDR4-2800 (~30–35 GB/s sustained bandwidth) per token. That physical bottleneck caps token generation at ~2.5–3.2 tokens/sec, meaning a single 4,000-token thinking + coding turn requires 21–26 minutes in decoding alone, before counting multi-turn prompt prefill.

E. Deep Technical Resolution and Controlled Tuning Sequence

Resolution of Core Runtime and Architectural Questions

Weight Quantization vs. Model Scale and Active Parameters

Empirical evidence from both the operator's local tests and upstream quantization benchmarks establishes that architecture class, active parameter routing, and multi-turn thinking preservation outweigh minor weight-quantization increments above 4-bit dynamic precision. Locally, the operator demonstrated on Qwen3.8-27B that Q6 (low/medium/xhigh) and Q8 (xhigh) achieved identical pass rates on the 16-check coding-boundary task and 5-check source task once a grading bug was corrected, showing zero Q8 quality advantage over Q6. Unsloth's Dynamic 2.0 quantization (UD-Q4_K_M and UD-Q4_K_XL) selectively keeps sensitive attention projections, MoE routers, embeddings, and output heads in Q6_K/Q8_0/FP16 while compressing routed expert FFN blocks to 4-bit, achieving state-of-the-art mean KL divergence across 21 of 22 model sizes. Consequently, stepping down to a higher-precision smaller dense model (such as a 12B–14B Q8_0 checkpoint) sacrifices the broad 35B expert capacity needed for multi-file repository comprehension, while stepping up to Qwen3.6-35B-A3B UD-Q5_K_M (+4.025 GiB) with apps open starves the host of system RAM.

Orthogonal Roles of Weight Quantization, KV Precision, Cache Placement, Layer Placement, and Dynamic Expert Caching

Each memory and placement flag in llama.cpp b11562 governs a distinct physical subsystem on the Ryzen 5800X + RTX 3080 workstation:

Weight quantization (UD-Q4_K_M, QAT Q4_0) compresses static parameters on disk and in memory; for CPU-resident weights, bit-width directly determines token generation speed because the CPU must transfer active weights across the dual-channel DDR4-2800 bus on every generated token. KV cache precision (--cache-type-k q8_0 --cache-type-v q8_0 vs. q4_0 or f16) compresses the dynamic activation history of tokens in context, where quantizing the V cache requires Flash Attention (-fa on, which llama.cpp enables automatically unless turned off). On Qwen3.6-35B-A3B, dropping KV from q8_0 to q4_0 at 64K saves only 340 MiB total (272 MiB on GPU) while risking degradation in exact path and line-number recall across 15 files; therefore, q8_0 KV should be retained. Experimental community forks such as llamampere or llama.cpp-adaptive-kv-streaming (which implement custom turbo or kvarn KV formats) are not tested on Windows mainline builds and are unnecessary when Qwen3.6's 64K q8_0 attention cache is only 680 MiB.

For KV cache placement, llama.cpp enables -kvo (--kv-offload) by default, allocating each layer's KV cache on the device that holds that layer. The flag to force the entire KV cache into system RAM is -nkvo (--no-kv-offload); the claim that --offload-kqv means RAM-only cache is backwards. Furthermore, when CUDA is enabled, llama.cpp allocates host-resident KV cache in CUDA_Host pinned physical memory to support asynchronous DMA transfers. Passing -nkvo on Qwen3.6-35B-A3B would free only 544 MiB of GPU VRAM while consuming 544 MiB of non-pageable host RAM and forcing attention layers to read keys and values over PCIe. Likewise, on dense models (Qwen3.8-27B or Gemma 4 31B), all-RAM KV does not resolve the prefill bottleneck: the retired dense setup already kept most layers (and their KV cache) on CPU, and its 42.6-minute prefill delay was caused by CPU dense matrix multiplication (mul_mat) across >20 GiB of weights rather than GPU KV capacity.

For layer, FFN, and expert placement, -ngl N offloads the output layer plus the last N−1N-1N−1 repeating blocks to GPU (Qwen3.6-35B-A3B has 40 blocks + 1 output layer = 41 offloadable layers). The flag --n-cpu-ffn N (-ncffn) keeps dense FFN weights of the first NNN layers on CPU (used for dense models), --n-cpu-moe N (-ncmoe) keeps MoE routed expert weights of the first NNN layers on CPU while leaving attention/DeltaNet and shared experts on GPU (for layers covered by -ngl), and --cpu-moe (-cmoe) keeps all routed MoE expert weights on CPU across all layers. In Configuration 1.4, setting -ngl 30 -ncmoe 33 leaves the first 11 layers entirely on CPU (including their Gated Attention/DeltaNet projections, shared experts, and 136 MiB of KV cache) while placing 7 full MoE expert layers on the GPU. Switching to -ngl all --cpu-moe (or -ngl all -ncmoe 35) places all 40 layers' attention, DeltaNet recurrent state, shared experts, output head, and 100% of the KV cache on the RTX 3080 GPU while keeping all 40 routed expert layers in CPU RAM—simultaneously accelerating prefill and reducing process VRAM from 5.88 GiB to ~5.09 GiB.

With respect to --moe-cache-mib N (merged via PR #29887 and #30112 right before b11562), this flag allocates an N MiBN\text{ MiB}N MiB GPU VRAM cache for CPU-resident MoE experts, transferring active experts over PCIe on cache misses. Community tests on an RTX 3080 10 GB running Qwen3.6-35B-A3B (UD-Q4_K_XL, 128K context, q8_0 KV) show that combining -cmoe with --moe-cache-mib raised decode speed from 34 tok/s to 53 tok/s (+56%), but reduced prefill speed from 539 tok/s to 453 tok/s (-16%) while filling VRAM to 9.5 GB. Similarly, tests on Gemma 4 26B-A4B QAT showed prefill dropping from 869.7 tok/s (no cache) to 625.6 tok/s (--moe-cache-mib 2000) and 409.3 tok/s (--moe-cache-mib 8000) because large prefill batches activate nearly all 128–256 experts per layer, thrashing the PCIe cache. Because this workstation has ~3.0+ GiB of VRAM occupied by desktop apps and processes prefill-heavy repository prompts, filling VRAM with --moe-cache-mib risks tripping the 400 MiB VRAM stop floor and slowing prefill; static placement (-ngl all --cpu-moe) should be validated first, and any subsequent test of --moe-cache-mib must be capped at 1024 MiB.

Speculative Decoding / MTP and Alternative Windows Runtimes

Although Qwen3.6-35B-A3B (unsloth/Qwen3.6-35B-A3B-MTP-GGUF), GLM-4.7-Flash, and Gemma 4 provide Multi-Token Prediction (MTP) / assistant draft heads, primary llama.cpp benchmarks (PR #23398) confirm that while MTP more than doubles generation speed on dense models (Gemma 4 12B and 31B), it yields little to no speedup on MoE models (26B-A4B and 35B-A3B). Verifying KKK draft tokens in a single forward pass on a CPU-offloaded MoE activates up to K×K\timesK× as many distinct routed experts per layer, multiplying the DDR4-2800 memory bandwidth required per step and negating the draft benefit. Regarding alternative engines (vLLM, SGLang, KTransformers, ik_llama.cpp, and Strata), vLLM and SGLang run on Linux/WSL2 and target full-VRAM GPU servers rather than hybrid 6 GiB VRAM + 21 GiB RAM split offloading, while Strata and ik_llama.cpp require custom Windows compilation and non-standard harness adapters. Remaining on mainline llama.cpp (b11562) on Windows is therefore fully justified.

Correction of Unsupported Heuristics

Several widespread rules of thumb in local LLM forums are refuted by primary architectural facts and the workstation's own measurements: "3-bit always breaks syntax" and "Q6 guarantees no coding errors" are disproven by Unsloth's UD-IQ3_S / UD-Q3_K_XL dynamic quants maintaining valid syntax while Qwen3.6 Q4 at temp 1.0 introduced semantic aliasing bugs and Qwen3.8 Q6 vs. Q8 showed identical accuracy; "MoE Q6 equals dense Q4" is false because a 35B-A3B MoE stores 35B parameters of domain knowledge across 256 experts but routes through a 3B active bottleneck per token; "Qwen3-Coder-30B is dense" is false because Qwen3-Coder-30B-A3B-Instruct is a 30.5B total / 3.3B active MoE model; and a universal "32K context uses 16 GB KV" rule is false because 64K q8_0 KV + state takes 742.81 MiB on Qwen3.6-35B-A3B, ~655 MiB on Gemma 4 26B-A4B, and 3,264 MiB on Qwen3-Coder-30B-A3B.

Context Capacity vs. Prefill Time, Editor Pruning, and State Preservation

Whether 32K, 64K, or 128K context can finish useful real-file work within 20 minutes depends on prefill compute time and prompt cache hit rate, not just KV cache memory fit. At 150–250 tok/s prefill, a cold 32K prompt takes 130–210 seconds (2.2–3.5 minutes), leaving over 16 minutes for multi-turn tool calls and deliberation. By contrast, an uncached 100K–128K prompt requires 400–850 seconds (6.7–14.2 minutes) for a single prefill pass, meaning two consecutive tool turns with cache misses will breach the 1,200-second cutoff even though the 1,423 MiB KV cache fits in VRAM. Thus, keeping the server at --ctx-size 65536 with Copilot budgeted at 32K input / 24K output (and Continue at 40K context / 24K output to bypass Continue 2.0.0's default 1,000-token output pruner reservation) is optimal for the apps-open state.

Crucially, llama-server in b11562 defaults -cram, --cache-ram N to 8192 MiB (8 GiB) and --cache-idle-slots to enabled. Over a multi-prompt session, llama-server can silently accumulate up to 8 GiB of cached prompt chunks in system RAM—explaining why free system RAM can unexpectedly dip below the 2.5 GiB emergency monitor floor and trigger an offline server incident! Explicitly passing --cache-ram 1536 (capping RAM prompt cache at 1.5 GiB) alongside --slot-save-path E:\llm\cache\slots bounds host RAM usage while allowing slot KV states to persist on disk. Furthermore, because KV cache is transient activation state that gets wiped whenever the editor prunes or compacts history, project instructions and task decisions must be preserved by writing compact checkpoints to docs/tasks.md and docs/prompts.md and enforcing a strict workflow rule that the model re-reads modified source files and task records via tool calls after any edit or compaction event.

Native Template and Deliberation-History Transport Across Families

Each model family transports internal deliberation differently across multi-turn tool loops. Qwen3.6-35B-A3B wraps internal thoughts in <think>...</think> and supports both enable_thinking (true/false) and preserve_thinking (true/false), where preserve_thinking: true retains prior assistant thought blocks across tool calls as recommended by the Qwen team for agentic coding. GLM-4.7-Flash uses enable_thinking (default true) and clear_thinking (false activates Preserved Thinking mode across tool turns; true clears prior thoughts). Gemma 4 (26B-A4B and 31B) requires the <|think|> control token at the start of the system prompt (enable_thinking defaults to false upstream) and emits <|channel>thought\n...; its July 2026 template update (discussions/35 and discussions/42) scopes preserve_thinking to tool-call continuation turns while omitting thoughts from standard chat history. None of these three checkpoints implement trained OpenAI-style reasoning_effort levels (low/medium/high/xhigh); passing those fields in API payloads is ignored by their Jinja templates.
